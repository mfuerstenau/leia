# ADR 0073 — Official Lucene jars, a class loader per runtime, and `--download-runtimes`

- **Status:** Accepted
- **Date:** 2026-10-14
- **Supersedes:** ADR 0044 §1 (relocation, and its rejected alternative of separate class loaders)
- **Amended by:** ADR 0077 (`--download-runtimes` lists the jars and asks first; `--yes`); ADR 0078 (the runtimes in a catalog, not in `RuntimeFolders.KNOWN`); ADR 0079 (§7: a dialogue, per-runtime failures, cancel); ADR 0080 (the folders load at startup and on `loadRuntimes`; the download inside leia); ADR 0098 (`runtimes/` beside `leia.jar` or in the user's data folder; leia's own jars refreshed at startup, an outdated adapter refused); ADR 0124 (§7: a list of mirrors, tried in order, instead of one repository); ADR 0125 (§7: a jar is copied from the local Maven or Gradle cache first)
- **Amends:** ADR 0004 (release folders without `runtimes/`); ADR 0065 §4 (step 5 dropped, steps 6 and 7 as built here); ADR 0068 §2 (old runtimes see no `--jar` jars); ADR 0072 (the layout of `runtimes/`); AGENTS.md hard rule 5, the architecture and the CLI contract

## Context

The Distribution lane (ADR 0065 §4) planned to publish leia's five runtime shadow jars to Maven Central and to have `leia.jar` download them. Each shadow jar is about 99% relocated Lucene and 1% leia: the adapters are 55 KB (lucene3), 63 KB (lucene5), 74 KB (lucene7), 143 KB (lucene9) and 53 KB (lucene10) plus 335 KB of leia-core. Relocation existed only because every Lucene uses `org.apache.lucene` and every runtime sat in one class-loader chain (ADR 0044 §1). Publishing would have needed a Central account and namespace, signing, POM metadata and a license review of the relocated Lucene, and a SNAPSHOT build would have had nothing to download.

Since ADR 0072, `leia.jar` holds no Lucene at all. A class loader whose parent sees only the JDK and the runtime interface therefore sees exactly one Lucene: its own.

## Decision

1. **Each old runtime gets a class loader of its own, over the official Lucene jars.** `runtimes/` beside `leia.jar` holds a folder per runtime: `lucene3`, `lucene5`, `lucene7`, `lucene9`, `lucene10`. Each has the runtime's adapter jar, `leia-luceneN.jar` (the module's plain jar, leia's code only), and the jars of the module's runtime classpath, as Gradle resolved them: the official `lucene-*.jar`s and, for Lucene 10, leia-core's jar. leia-server's `RuntimeFolders` loads an old runtime through a `URLClassLoader` over these jars whose parent, `ApiOnlyLoader`, hands `io.github.mfuerstenau.leia.runtime.*` to leia's loader and everything else to the platform loader. Neither leia's other classes, nor the test classpath, nor the jar chain's Lucene 10 reach it, nor their resources.
2. **Lucene 10 stays in the jar chain.** Its folder's jars are the first link of `JarChain`, as `leia-lucene10.jar` was (ADR 0065 §2, ADR 0072 §2), since the jars of `--jar` link against its Lucene.
3. **Each adapter carries its folder's list**, `META-INF/leia/runtime.txt`, written by build-logic's `RuntimeListTask` from the module's resolved runtime classpath: per jar the file name, SHA-256 and size, and for a jar from Maven Central its path there. Jars without a path are leia's own (leia-core); `leia.jar` brings them. The list is the one source of truth: the server reads it to load exactly the listed jars and to see whether a folder is complete; `--download-runtimes` reads it to know what to fetch and check. The SHA-256s are those of the very files Gradle resolved, and Lucene versions are fixed releases, so a SNAPSHOT of leia downloads as well as a release.
4. **A folder that is missing, incomplete or refused is not fatal.** `RuntimeFolders.State` is `Loaded`, `Missing` (no folder or no adapter), `Incomplete(jar)` (the first listed jar that is absent; nothing is loaded) or `Refused(reason)` (no list, a runtime for another interface version, no runtime in it). leia starts all the same; `getRuntimes` reports each runtime's state (`RuntimeFolder` with `RuntimeState` `LOADED`/`MISSING`/`INCOMPLETE`/`REFUSED` and an optional `problem`, replacing `RuntimeJar`), and the about screen lists them. Only `--jar` and `X` jars still fail with `INVALID_JAR`. Folders load once per JVM, like the jar chain; a loaded folder stays loaded. `LeiaBackend.start(Optional<Path> runtimesDir, List<Path> jars)` takes the folder.
5. **Lucene 5.5's SPI goes through the context class loader.** Its `NamedSPILoader(Class)` and `AnalysisSPILoader` read the thread's context class loader, which on the backend thread is the jar chain's and sees Lucene 10's services files: Lucene 10's codec classes were cast to 5.5's `Codec` and failed with a `ClassCastException` (checked by removing the fix: `Lucene5BackendTest` fails). 7.7 and 9.12 use the class's own loader. `Spi.initialize(anchor, init)` in `leia-runtime`'s `support` package (ADR 0050) sets the context class loader to the runtime's own while `Lucene5Runtime`'s constructor builds the lists of codecs, formats and analysis factories; they stay built.
6. **Build.** `leia.lucene-runtime-conventions` drops Shadow, the relocation and the `-plain` classifier, and applies the new `leia.runtime-folder-conventions`, which leia-lucene10 applies too: the jar is `leia-luceneN.jar`, `runtimeList` writes the list into it, and `adapterJarCheck` (`AdapterJarCheck`, replacing `RelocationCheck` and leia-lucene10's `excludedPackagesCheck`) fails on any class outside the runtime's package (plus `org/apache/lucene/index/RawPostings` for lucene3, ADR 0062; `lucene-core-3.6.2.jar` isn't sealed) and on any services file but the runtime's. Consumers resolve a module's `runtimeElements` transitively (`runtimeFolderJars` in build-logic). leia-tui's `leiaFolder` writes the five folders; `:leia-tui:run` passes `-Dleia.runtimes=build/leia/runtimes`, which `Platform.runtimesDir()` honours.
7. **`--download-runtimes`** installs the folders, then exits. `leia.jar` embeds leia's own jars of each folder under `leia-runtimes/<folder>/` (about 0.7 MB); `noLuceneInJarCheck` also refuses a nested `lucene-*.jar`. `RuntimeInstall` writes leia's jars from there and downloads Lucene's from `https://repo1.maven.org/maven2/` (`-Dleia.download.url` for tests and mirrors) through the JDK's `HttpClient`, honouring `-Djava.net.useSystemProxies=true`. Each download goes to a temporary file in the folder while it is hashed, is checked against the list's SHA-256 and size, and moves into place; a jar that is there and matches is kept; jars and leftover downloads the list doesn't name are removed. One line per jar goes to stdout; a failure names the jar and the URL on stderr and exits 1. It runs right after `--version`, before any jar is loaded, so that no runtime jar is open (Windows wouldn't replace it) and the terminal is still leia's. It takes no index path and no other option (exit 2), and needs `leia.jar` or `-Dleia.runtimes` (exit 1).
8. **Slim dist.** `build-dist.sh` copies `leia.jar`, `leia` and `leia.cmd` only. `MISSING_RUNTIME` names the runtime's folder (`runtimes/lucene9`) and the TUI adds "install it with leia --download-runtimes"; the about screen and `--help` point there too.

## Alternatives considered

- **Publish the shadow jars to Maven Central** (ADR 0065 §4 step 5). It ships 99% Lucene again under leia's coordinates, needs an account, namespace, signing and POM, and leaves SNAPSHOT builds with nothing to download.
- **Keep relocation and download the shadow jars from GitHub releases.** No account needed, but the jars are still large, SNAPSHOTs still have none, and the hashes would be of files built elsewhere.
- **Set the context class loader around every runtime call** instead of initialising 5.5's lists once. More code on every call path, for one Lucene; kept as the fallback if a lazy path ever escapes.
- **Download and then start leia.** The user asked for download-then-exit: it keeps the command's output on the terminal and its exit status meaningful for scripts.

## Consequences

- An old runtime can no longer come through `X` or `--jar`, which would need its Lucene in the chain; Lucene 10 can, by adding the `runtimes/lucene10` directory. An old runtime's loader could take `--jar` jars of its own Lucene (ADR 0068 §2); not done.
- The release folders are about 7 MB instead of 38 MB, and the first run needs the network once.
- The tests load the old runtimes as leia does: leia-server's and leia-tui's `testRuntimes` put the folders together, passed as `-Dleia.test.runtimes`, while Lucene 10 stays on the test classpath; the `Lucene*BackendTest`s now also cover the isolation and the context class loader. leia-server's `jarsTest` loads all five folders on a classpath without Lucene, and covers an incomplete and a refused folder; `RuntimeInstallTest` runs against the JDK's `HttpServer`.
- A new runtime is one module with the conventions, one entry in `RuntimeFolders.KNOWN` and one in build-logic's `RUNTIME_MODULES`. (Since ADR 0078: one entry in the runtime catalog instead of `KNOWN`.)
